# S4 QA dependency content provenance

Status: design for GPT-PM MAJOR-02 from the correlated review of candidate `3b8d80ff5456192c2419d9515b47fb843939ee16`. Implementation and runtime evidence are pending. This design does not authorize network access, installing during a run, CI, or execution of any policy-excluded selector.

## Problem

`tools/qa/run.py::_lock_versions` currently parses package names, versions, and SHA-256 text from `tools/qa/requirements.lock`. `_installed_versions` checks only distribution names and versions in the external dependency target. The report records the lock digest and versions, but not the wheel bytes or installed package file contents. A modified target can therefore retain matching package metadata and pass the current gate.

## Contract

1. Environment preparation remains separate from execution and consumes only an already-present wheelhouse. It verifies each selected wheel against the exact hash in the lock and writes a fresh external target from those verified bytes. It performs no download or package-index access and never overlays an existing target.
2. The run command receives both the external dependency target and the external wheelhouse. Before starting pytest, it parses the lock, requires exactly one applicable wheel per locked distribution, checks every wheel's SHA-256 against the lock, validates the wheel's name/version/platform metadata, and derives the allowed installed file inventory from the wheel's `RECORD` entries.
3. The target inventory must equal the supported wheel installation layout. Every installed file must match the corresponding wheel file digest and size. Missing, extra, linked, non-regular, unsupported-layout, hash-mismatched, or version-mismatched files produce a typed non-approving report. The runner does not trust target `METADATA` or `RECORD` as the authority; expected file data comes from the hash-verified wheel archive.
4. Unsupported wheel layouts fail closed. The initial implementation may support only the pure Python wheel tags and direct `purelib` layout used by the locked QA set. It must reject `.data` relocation, native extension files, path traversal, duplicate normalized paths, ambiguous wheel matches, and unrecognized executable/importable files rather than guessing pip transformations.
5. Set `PYTHONDONTWRITEBYTECODE=1` for pytest so runtime-generated bytecode does not become an unaccounted dependency file. Do not expose the absolute wheelhouse or dependency-target paths in reports.
6. Record normalized package-to-wheel SHA-256 values, the dependency target content digest, and verification state in the report. Recompute the supported target inventory after pytest; any change makes the result non-approving. Keep lock hashing and matrix verification bound to the same report fields.
7. The runner remains offline and does not install, download, repair, or refresh packages. The preparation utility is a separate explicit command; tests still run only through the authorized `functional-test-reviewer` or `e2e-runner` roles after implementation is complete.

## Threat boundary and limitation

Wheel hashes establish the selected package archive bytes against the committed lock. Comparing target file bytes with those verified archives closes the current same-version/content substitution gap. A pre-run and post-run inventory detects persistent target changes. This does not claim that Python tests are a sandbox against a malicious test process with the same account: such code can alter its process or environment while running. The OS sandbox and existing policy gates remain separate acceptance requirements.

## Acceptance

AC-17 in `docs/S4_QA_AUTOMATION_PLAN_2026-10-24.md` requires fail-closed behavior for a changed same-version module, a wheel/lock mismatch, an extra importable file, an unsupported wheel layout, and dependency-target mutation detected after execution. The report must bind verified wheel and target-content digests without absolute external paths. No runtime evidence exists yet.
